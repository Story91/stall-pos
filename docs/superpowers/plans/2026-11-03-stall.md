# Stall Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A voice-first PWA where a vendor speaks a sale, gets a PayPal invoice QR, hears "paid" via webhook, logs who they owe, and closes the day with an agent that pays through PayPal Payouts within code rules and holds suspicious bills.

**Architecture:** One Next.js App Router project in `stall/`. The hot sell path is deterministic (LLM parses speech → owner confirms → code builds the invoice via PayPal REST). The close path pre-computes rule outcomes in pure code, then an AI agent with three tools writes the summary and may only escalate payable items to holds. Postgres (Neon) via Drizzle; PGlite in tests; SSE + polling to the phone.

**Tech Stack:** Node 26, Next.js (latest stable, App Router), TypeScript strict, Tailwind, Drizzle ORM (`pg` driver prod, `@electric-sql/pglite` tests), Vitest, Playwright (one smoke), Vercel AI SDK 7 (`ai`) + `@ai-sdk/anthropic` (`claude-sonnet-5-5`), zod, PayPal REST (Invoicing v2, Payouts v1, Webhooks v1) via `fetch`, `@paypal/agent-toolkit` only for the stretch reminder tool, Render + Neon.

**Spec:** `docs/superpowers/specs/2026-11-03-stall-design.md` (v2). Read it first; the plan argues from it.

## Global Constraints

- Sandbox only: host `https://api-m.sandbox.paypal.com`; `PAYPAL_ENV=sandbox`; never log secrets or tokens.
- Money is integer **cents** internally; PayPal payloads use strings with exactly 2 decimals; currency `USD` everywhere.
- Every PayPal POST carries `PayPal-Request-Id`; every money action persists a one-sentence `rationale`.
- Close-the-day is idempotent: a shift/bill with a payout in `PENDING`/`SUCCESS` is never paid again; `sender_batch_id = stall-{businessId}-{shift|bill}-{id}`.
- The model never invents an amount; it acts only on owner-logged shifts/bills and only within rule outcomes computed in code; it can turn "pay" into "hold", never the reverse.
- Business date = `YYYY-MM-DD` in the business timezone (seed: `America/Chicago`).
- Everything that ships (code, UI copy, README) is English. Languages supported in parsing: `en`, `es`, `pl`.
- Core loop (Tasks 0–17) green end-to-end before any stretch task (18+). Commit after every task; `main` always runs.
- Seed business: "La Esquina", Austin TX, tax rate `0.0825`, payees Maria (prep cook, daily rate 12000 cents, max/day 15000, auto-pay) and Tortillería Rosa (supplier, max/day 20000, manual), demo-day bill 24000 cents "tortillas" plus a paid bill 24000 "tortillas" two days earlier.

## Review Focus

1. Transcript with no sellable content ("hello?", silence) → parser returns zero items and a spoken "I didn't catch an order"; no invoice is created. Test in Task 6.
2. Spoken prices in words or odd formats ("four fifty", "8.5", "$3", "dos con cincuenta") → normalized to cents; zero or negative price rejected before Charge. Test in Task 6.
3. Owner double-taps Charge → exactly one invoice (server idempotent on `draftId`). Test in Task 8.
4. Webhook `INVOICING.INVOICE.PAID` arrives for an invoice the DB does not know yet (race) or for an already-paid sale → stored as unmatched / ignored, never crashes, never double-marks; cash recorded after PayPal paid is rejected. Tests in Task 9 and Task 8.
5. Close runs while a payout from a previous run is still `PENDING` → that obligation is skipped, not re-paid; second run of the same day produces no new payouts or decisions. Test in Task 14 and Task 15.
